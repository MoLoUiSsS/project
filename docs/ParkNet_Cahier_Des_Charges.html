1. Présentation du Projet

1.1 Contexte

Dans un contexte d'urbanisation croissante et de numérisation des infrastructures, la gestion des accès aux parkings (publics ou privés) demeure souvent manuelle, coûteuse et sujette aux erreurs humaines. L'utilisation de barrières traditionnelles avec des agents physiques ou des systèmes à tickets engendre des files d'attente, des coûts de personnel élevés, et complique la traçabilité des entrées/sorties.

1.2 Objectif du Projet

Le projet ParkNet a pour vocation de concevoir et développer un système de contrôle d'accès de bout en bout, automatisé et intelligent. Il repose sur la technologie de Lecture Automatique de Plaques d'Immatriculation (LAPI). Le système doit pouvoir : - Détecter physiquement l'approche d'un véhicule. - Capturer l'image de sa plaque d'immatriculation. - Analyser cette image via un service d'OCR (Optical Character Recognition). - Autoriser ou refuser l'accès en fonction d'une base de données centralisée. - Piloter l'ouverture de la barrière de manière autonome.

1.3 Périmètre

Le système couvre à la fois : - La dimension matérielle (IoT) : Capteurs, microcontrôleur, actionneurs, et dispositif de capture (smartphone). - La dimension logicielle : Serveur local temps-réel, traitement d'images, intégration d'API cloud, et interface d'administration (Dashboard).

3. Expression des Besoins

3.1 Besoins Utilisateurs (User Stories)

  • En tant qu'administrateur du parking, je veux visualiser en temps réel l'état de la barrière et les passages de véhicules, afin de surveiller le parking à distance.
  • En tant qu'administrateur, je veux pouvoir inscrire de nouveaux véhicules et gérer leurs abonnements (paiements, liste noire, liste blanche).
  • En tant qu'usager, je veux que la barrière s'ouvre automatiquement sans que j'aie à présenter de badge ou de ticket, à condition que je sois enregistré et à jour de mes paiements.
  • En tant qu'auditeur, je veux pouvoir consulter l'historique complet des accès (autorisés et refusés) avec des preuves photographiques, pour résoudre d'éventuels litiges.

3.2 Acteurs du Système

  • L'Usager (Automobiliste) : N'interagit pas directement avec une interface numérique, mais interagit physiquement avec les capteurs et la barrière.
  • L'Administrateur : Gère le système via un Dashboard web sécurisé.
  • Le Système IoT : Agit de manière autonome pour orchestrer la détection et la capture.

4. Exigences Fonctionnelles

Identifiant Fonctionnalité Priorité Description
EF-01 Détection de présence Indispensable Le système doit détecter la présence d'un véhicule à une distance paramétrable (ex: < 30 cm) à l'aide d'un capteur ultrasonique.
EF-02 Capture photographique Indispensable Le système doit déclencher la prise d'une photographie HD via une caméra IP / Smartphone connecté.
EF-03 Reconnaissance LAPI (OCR) Indispensable Le système doit extraire le texte de la plaque d'immatriculation algérienne à partir de l'image capturée.
EF-04 Vérification des droits Indispensable Le système doit interroger la base de données locale pour vérifier le statut du véhicule (Inscrit, Payé, Blacklisté).
EF-05 Contrôle de la barrière Indispensable Le système doit piloter l'ouverture (90°) et la fermeture (0°) automatique d'un servo-moteur en fonction du résultat de vérification.
EF-06 Dashboard d'administration Indispensable Une interface web doit afficher l'état du système en temps réel, le flux vidéo/images, et les derniers accès.
EF-07 Gestion des véhicules (CRUD) Indispensable Interface permettant d'ajouter, modifier, supprimer des véhicules et mettre à jour leur statut.
EF-08 Historisation (Logs) Importante Tout accès ou tentative d'accès doit être enregistré en base de données avec l'horodatage, l'image associée et le motif de refus s'il y a lieu.
EF-09 Mode Fallback OCR Souhaitable En cas de panne de la connexion internet (impossibilité d'utiliser l'API Cloud), le système doit basculer sur un moteur OCR local (ex: Tesseract).

5. Exigences Non-Fonctionnelles

  • ENF-01 - Temps de réponse : Le processus complet (Détection → Capture → OCR → Décision → Ouverture) doit s'exécuter en moins de 15 secondes pour garantir la fluidité du trafic.
  • ENF-02 - Précision OCR : Le taux de reconnaissance correcte des plaques doit être supérieur à 90% dans des conditions d'éclairage normales, grâce au pré-traitement des images (CLAHE, Sharpening).
  • ENF-03 - Fiabilité (Anti-rebond) : Le système de détection doit intégrer un délai de "debounce" (ex: 5 secondes) pour éviter les captures multiples et intempestives d'un même véhicule.
  • ENF-04 - Déploiement : L'application serveur doit pouvoir être déployée sur n'importe quelle machine Windows/Linux capable d'exécuter Python 3.10+, sans dépendances complexes.
  • ENF-05 - Interface Utilisateur : Le Dashboard doit proposer une ergonomie premium (Design moderne, Glassmorphism, animations fluides) adaptée aux écrans desktop.

6.2 Architecture Matérielle (IoT)

  • Microcontrôleur : Arduino Uno R3.
  • Capteur de distance : HC-SR04 (Ultrasons).
  • Actionneur : Servo-moteur SG90 (simulation de la barrière).
  • Dispositif de capture : Smartphone (utilisant sa caméra principale via l'API Web getUserMedia).
  • Communication Hardware/Software : Protocole UART série sur USB (Baudrate: 9600).

6.3 Architecture Logicielle (Serveur & Backend)

  • Langage de programmation : Python 3.10+
  • Framework Web : Flask (Architecture par Blueprints pour la modularité).
  • Communication Temps Réel : Flask-SocketIO (WebSocket) pour faire le pont entre la caméra (Smartphone), le Serveur, et l'Interface d'Administration.
  • Traitement d'Image : OpenCV (cv2) pour l'amélioration de la qualité avant l'OCR.
  • Service LAPI / OCR : API Cloud OCR.space (avec gestion de rate-limiting et clés multiples) + Fallback local pytesseract.

8. Contraintes & Risques

Risque Identifié Impact Solution Apportée / Mitigation
Plaques sales ou détériorées Baisse du taux de reconnaissance OCR. Amélioration logicielle des images (Contraste adaptatif) ; Interface manuelle pour que l'admin déclenche l'ouverture au cas où.
Limitation d'accès API (Rate limit) Blocage complet de la reconnaissance (Erreur 429). Rotation implémentée sur plusieurs clés API gratuites. Algorithme de bascule automatique vers Tesseract en cas de limite atteinte.
Sécurité Web (HTTPS requis pour la caméra) Le navigateur bloque la caméra en HTTP simple. Accès via IP locale directe, ou utilisation recommandée d'un tunnel sécurisé (Cloudflared).
Luminosité nocturne Caméra de smartphone inefficace dans le noir total. Déploiement physique prévu : ajout d'un projecteur LED sur le site réel.
